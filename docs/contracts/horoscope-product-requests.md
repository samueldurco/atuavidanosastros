# Saved natal profile to Horoscope — atv-horoscope-request/1

Local implementation only; `horoscope` remains disabled. The bridge does not approve its calculation, editorial profile, model or hosted release.

`POST /api/workflows/horoscope` accepts exactly `{requestKey,input}`. Input has exactly five fields, or six when context is present: `version: atv-horoscope-request/1`, `productId: horoscope`, positive integer `expectedRevision` below 2147483647, canonical Gregorian `targetDate` between 1900-01-01 and 2099-12-31, and exact `{storage:true,policyVersion:atv-input-consent/1,partner:false,continuity:false}` consent. Optional `context` must be non-whitespace valid Unicode, at most 1,200 UTF-16 units and 4,800 bytes, without C0 controls except tab/LF/CR or DEL/C1 controls. Omission is valid; present empty/null/whitespace values are rejected. Text is retained exactly.

The browser cannot supply birth data, owner, time precision, timezone, current location, aliases or broader cycle inputs. HTTP requires authenticated claims, same origin and a body of at most 8192 bytes. SQL independently validates the command and its 8192-byte envelope. Fixed errors and UUID-only acknowledgements carry private/no-store/no-referrer/noindex headers. Backend diagnostics never reach the client. A 202 acknowledges a saved request, not a ready reading.

`request_horoscope_product_run` obtains the existing owner advisory lock and then the active profile row lock. New commands require the expected onboarding revision and a COMPLETE, consented, EXACT natal profile. Only the six BirthInput fields enter the immutable workflow snapshot, together with the explicit date, optional report and separate storage consent. `request_product_run` retains release, entitlement, quota and atomic run/event/Library authority. The private `horoscope_product_requests` receipt records the exact command and natal version. Direct receipt access is revoked from public, anonymous, authenticated and service roles; the definer RPC has an empty search path and is authenticated-only.

An existing active owner/key with the identical command returns the original run before evaluating the current natal profile or release. This preserves acknowledgement recovery after profile edits/removal and gate closure. Changed commands and keys used by other request bridges are refused. Forgetting onboarding preserves existing product snapshots; deleting a run cascades the receipt. `supabase/forward-fixes/disable_horoscope_product_requests.sql` revokes this bridge while preserving history and UUID-only read recovery. Reapplying the additive migration restores scoped execution and original retries. No existing bridge or generic RPC contract is changed.

The intake reads the saved profile explicitly, leaves the date blank, invalidates consent on date/report edits and clears drafts after submission. Session storage keeps only the UUID. After uncertainty or reload the client performs read recovery, with no automatic write replay or profile read. The report/date/natal data never enter browser storage, telemetry, the natal profile or ATV+ memory through this intake.

The own Horoscope calculation contract remains authoritative: one geocentric sample at 12:00 UTC, 121/122 facts and one hundred directed nominal pairs whose precision is uncertified and stability unknown. Birth timezone does not establish current location or local-day coverage. General forecasts for twelve signs, daily/weekly/monthly recurrence, alerts, annual history/renewal and the full funnel remain separate requirements.
