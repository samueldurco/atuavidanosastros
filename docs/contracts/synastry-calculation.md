# Synastry calculation — atv-synastry-calculation/1.0.0

WU156 composes an internal, experimental `synastry` calculator from two validated natal charts and the existing [cross-aspect engine](astrology-cross-aspects.md). `createSynastryCalculators(policy, provider)` requires a detached, validated `AspectPolicy`; there is no default editorial policy. The default product runtime has no Sinastria calculator. This factory is an internal composition boundary, not an HTTP endpoint or product release.

The exact workflow input requires valid birth records for A and B, storage consent, partner consent and the existing consent policy version. Both civil records are checked before provider work. The accepted input and operator policy are captured before asynchronous calculation; client policy fields are rejected. Abort fences apply before work and after each provider result. Each chart must satisfy the existing experimental natal boundary, including the tropical, apparent geocentric ecliptic reference frame. Provider output is captured before calculating the next person.

The projection retains ten canonical positions per person and independent provenance for both charts. Positions expose only body, longitude, latitude, distance and retrograde status. It does not project raw birth records, names, gender, houses or angles. Twenty calculated facts use separate `person-a-*` and `person-b-*` IDs. Their sources bind provider/version, algorithm and this contract. Optional consented context is a reported `personal-context` fact, never a geometric input.

All 100 ordered A/B body pairs are evaluated and retained, including same-body pairs and nominal absences. Each `cross-<body-a>-<body-b>` calculated fact displays its nominal circular separation and either the configured aspect and nominal deviation or the absence of a configured aspect within its nominal orb. Facts bind the geometry algorithm, stability algorithm, policy ID/version and this contract. Exact geometry remains numeric in the snapshot; display values have six decimal places. No ranking, top-N selection or truncation discards a pair.

The two longitude error budgets remain `null`: neither birth precision nor ephemeris accuracy has been certified. Consequently, all 100 stability assessments are `unknown`, including nominal absence. Applying/separating motion and exact events are not evaluated. A nominal match is not a robust aspect, and a nominal absence does not certify the absence of an aspect. The policy's editorial approval is explicitly `not-established`.

The snapshot is experimental and partial. `sharing` is `not-authorized`, `compatibilityScore` is `null`, and `events` is empty. Recorded consent does not prove identity, bilateral authorization or permission to share. The output supplies no interpretation, compatibility score, feelings, gender, behavior or relationship destiny. Provider warnings and all calculation, precision and consent limits remain attached.

The existing calculation envelope bounds and detaches the output: at most 400 unique facts, sources up to 300 characters, displays up to 2,000 characters, up to 32 limitations and at most 200,000 UTF-8 bytes. This projection normally has 120 facts, or 121 with reported context. Invalid provider output or an invalid envelope fails with `calculation_invalid`; invalid input fails with `input_invalid`.

E2 requires complete, grounded relational interpretation and legitimate editorial/model approval; E3–E5 require integration, private persistence, final web/PDF delivery and the complete accepted journey.
